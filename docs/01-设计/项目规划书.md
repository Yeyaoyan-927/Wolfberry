## 1. 项目目标与范围

### 1.1 业务目标

| 目标 | 衡量方式 | 目标值（上线 3 个月） |
|---|---|---|
| 建立可交易的枸杞货源市场 | 在架商品数 / 注册卖家数 | 在架 ≥ 3000，卖家 ≥ 200 |
| 用 AI 评估抑制"图文不符" | 审核环节拦截的高报率 | 高报（黄+红标）占比 ≥ 15%，即真实存在且被拦住 |
| 缩短买家决策链路 | 从进入详情到下单的转化 | 详情页 → 下单转化率 ≥ 8% |
| 降低审核人力成本 | 单商品审核耗时 | 平均 ≤ 90 秒/条 |
| 沉淀价格数据资产 | 成交价日聚合覆盖率 | 主流品种 × 主产区覆盖率 ≥ 80% |

### 1.2 技术目标

| 目标 | 指标 |
|---|---|
| 核心接口性能 | 商品列表 P95 ≤ 500ms，详情 ≤ 800ms，下单 ≤ 500ms |
| 主链路可用 | 99.5%（月度），AI 评估故障不阻塞交易 |
| 智能问答质量 | 引用准确率 ≥ 95%，无据作答 ≤ 3% |
| 图像评估 | 5 图 CPU 评估 ≤ 15s，等级与人工一致率 ≥ 80% |
| 可维护性 | 新增一个业务模块不改动既有模块代码（靠分层与事件解耦） |
| 可追溯性 | 任一商品可回溯"谁审的、AI 说了什么、当时阈值是哪版" |

### 1.3 范围

**本期建设（V1–V3，14 周）**

商品发布与审核、AI 图像评估、买家浏览与下单、订单履约、售后、评价、行情分析、智能问答、后台治理（用户/权限/知识库/模型/审计/看板）。

**明确不做**

在线支付与资金托管、物流轨迹、实验室理化检测、自营采购仓储、自动定价与自动上架、移动端 App、营销工具、跨境与多语言。

### 1.4 关键假设（不成立则需重新规划）

1. 卖家有能力上传清晰实拍图（≥3 张、短边 ≥1000px），否则 AI 评估价值大幅下降。
2. 平台有 1–2 名专职审核员，日均可处理 200–300 条。
3. 上线初期成交数据稀疏，行情模块需接受"参考行情 + 样本不足"的过渡态。
4. 买家与卖家共用一套前端，靠角色控制功能可见性（不做两套独立站点）。

### 1.5 约束

- 技术栈锁定：Vue 3 + JavaScript + Element Plus；Python + FastAPI + MySQL；智能体用 RAG + Agent + LangChain + LangGraph。
- 无 GPU 也必须能跑（图像评估用 ONNX CPU 兜底）。
- 不引入消息队列、不引入独立向量库（用 MySQL + faiss 本地索引）。

## 2. 总体建设思路

### 2.1 六条设计原则

| 原则 | 含义 | 反例（要避免的写法） |
|---|---|---|
| **分层单向依赖** | api → service → domain → repository → model，禁止反向 | Router 里直接写 SQL |
| **AI 只是能力，不是核心** | AI 故障时交易链路必须照常可用 | 商品详情强依赖评估服务，评估挂了页面白屏 |
| **判定走规则，生成走模型** | 等级、价格、库存、状态全用规则；LLM 只做语言组织 | 让 LLM 决定"这货是几级" |
| **写操作必留痕** | 审核、改价、状态变更、权限变更全部落审计 | 直接 UPDATE 无记录 |
| **异步优先** | 评估、入库、导出、通知全部异步，不占用请求线程 | 提交审核时同步等 15 秒评估 |
| **可降级** | 每个外部依赖都有降级路径与开关 | 第三方挂了整站 500 |

### 2.2 分层架构总览

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层   Nginx：HTTPS / 静态资源 / 限流 / 防盗链 / 上传体积限制        │
├──────────────────────────────────────────────────────────────────────┤
│ 前端     交易端 SPA (web)              后台 SPA (admin)                │
├──────────────────────────────────────────────────────────────────────┤
│ 接口层   FastAPI Router → 鉴权 → 参数校验(DTO) → 限流 → 统一响应/异常  │
├──────────────────────────────────────────────────────────────────────┤
│ 应用层   Service：用例编排 / 事务边界 / 事件发布 / 权限校验(数据级)     │
├──────────────────────────────────────────────────────────────────────┤
│ 领域层   Domain：等级判定、库存扣减、审核状态机、报价规则、订单状态机   │
├──────────────────────────────────────────────────────────────────────┤
│ 数据层   Repository → SQLAlchemy → MySQL    │  Storage：本地盘/NAS     │
├──────────────────────────────────────────────────────────────────────┤
│ 异步层   Worker（图像评估 / 知识入库 / 导出 / 通知）  +  Scheduler      │
├──────────────────────────────────────────────────────────────────────┤
│ 智能层   Agent(LangGraph) ──▶ Tools ──┬─▶ Vision(ONNX CPU)            │
│                                       ├─▶ RAG(faiss + bge + rerank)   │
│                                       ├─▶ SQL 查询模板（只读）         │
│                                       └─▶ 规则引擎（等级/价格）         │
│                          LLM Provider（可切换：云端 / 本地）           │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.3 两条主链路的请求走向

**链路 A：商品审核（写链路，异步为主）**

```
卖家提交 → Router → ProductService.submit()
        → 校验（资质/图片/字段/盗图）
        → 写 product(status=待审核) + product_version
        → 发事件 ProductSubmitted
        → 立即返回（不等评估）
                     ↓
        Worker 消费 → VisionService.assess()
        → 写 ai_assessment + 更新 grade_flag
        → 发事件 AssessmentReady → 进入审核队列
                     ↓
        审核员 → AuditService.approve() → 写 product_audit + 改 status
        → 发事件 ProductPublished → 更新搜索索引/行情/通知卖家
```

**链路 B：智能问答（读链路，同步流式）**

```
用户提问 → Router → ChatService.send()
        → 建/取 session → 构造 state → 启动 LangGraph(astream)
        → SSE 逐段推送（stage/delta/citation/done）
        → 落库 chat_message + agent_trace
        → 异步更新会话摘要
```

> 两条链路彼此独立：审核链路慢不影响问答，问答的 LLM 故障不影响审核。

## 3. 功能模块划分

### 3.1 模块全景

|---|---|---|
| **交易域** | 商品 Product | 发布、编辑、上下架、版本 |
| | 审核 Audit | 队列、工作台、通过/驳回/改级、统计 |
| | 订单 Order | 下单、确认、发货、收货、取消 |
| | 售后 AfterSale | 申请、举证、响应、仲裁 |
| | 评价 Review | 评分、内容、申诉 |
| | 行情 Market | 成交聚合、挂牌价、参考行情、图表 |
| **用户域** | 认证 Auth | 注册、登录、令牌、改密 |
| | 用户 User | 资料、状态、角色绑定 |
| | 卖家 Seller | 资质准入、店铺、违规、评分 |
| | 权限 RBAC | 角色、权限点、菜单、数据范围 |
| **智能域** | 图像评估 Vision | 门禁、推理、后处理、汇总、等级建议 |
| | 知识库 KB | 文档、分块、入库任务 |
| | 检索 RAG | 向量+关键词召回、重排、引用 |

### 3.3 补充的完善性功能（需求文档未明写，工程必需）

这 12 项不属于业务功能，但缺了会出问题。全部纳入 **平台域**，由专人一次性建设，各业务模块复用。

| # | 能力 | 解决什么问题 | 实现要点 | 使用方 |
|---|---|---|---|---|
| 1 | **统一权限模型** | 前端隐藏按钮不等于安全；越权查他人订单 | RBAC（角色-权限点）+ 数据权限（site/seller/buyer 归属）+ 接口装饰器声明 + Repository 层强制拼接归属条件 | 全部模块 |
| 2 | **操作审计** | 谁改了价格、谁驳回了商品、谁改了阈值 | 装饰器 `@audit(action, resource)` 自动记录操作人、对象、改前值、IP、trace_id；只增不删 | 商品、审核、订单、权限、配置 |
| 3 | **全局异常体系** | 各处 try/except，报错文案五花八门 | 错误码枚举（业务码 + HTTP 码）+ `BizException` 家族 + 全局 handler + 未捕获异常兜底 + 生产环境隐藏堆栈 | 全部 |
| 4 | **分层配置管理** | 改个阈值要改代码重新发布 | 优先级：环境变量 > DB `sys_config` > 环境 yaml > 默认 yaml；支持热更新（60s 轮询）与变更审计 | 全部 |
| 5 | **幂等控制** | 网络抖动导致重复下单、重复提交审核 | `Idempotency-Key` + Redis-free 方案（`idempotency_record` 表，唯一索引 + 过期清理） | 下单、提交商品、评估触发 |
| 6 | **限流与防刷** | 恶意刷接口、爬商品、撞库 | 进程内令牌桶（单机足够）+ 按用户/IP/接口三维度；登录失败计数锁定 | Auth、商品列表、问答 |
| 7 | **统一文件服务** | 图片各处各写一套，格式不统一、原图裸奔 | 上传校验 → 重命名 → 二次编码（去恶意 EXIF）→ 压缩 → 缩略图 → 计算 MD5/pHash → 存路径；对外只给带签名的临时 URL | 商品、资质、售后举证、知识库 |
| 8 | **异步任务框架** | 评估/入库/导出抢请求线程 | `job` 表 + 状态机 + `FOR UPDATE SKIP LOCKED` 抢占 + 重试退避 + 超时置失败 + 死信可查 | Vision、KB、导出、通知 |
| 9 | **数据字典** | 枚举散落在代码与前端，加一个值要改三处 | `sys_dict` + `sys_dict_item`，前端启动拉取并缓存，后端校验引用 | 商品、订单、审核 |
| 10 | **健康检查与就绪探针** | 服务挂了但不知道，负载均衡还在打流量 | `/health`（存活）+ `/ready`（依赖就绪：DB/模型/索引）+ `/metrics`（关键计数） | 运维、监控 |
| 11 | **灰度与降级开关** | 新功能出问题只能回滚代码 | `feature_flag`（按用户/比例/白名单）+ `degrade_switch`（如"关闭 AI 评估""关闭问答"），DB 驱动、即时生效 | 全部 |
| 12 | **序列号生成器** | 订单号/商品号并发重复、可被猜测 | 号段模式（`seq_segment` 表）+ 业务前缀 + 日期 + 校验位；禁止用自增 ID 对外 | 商品、订单、报告、工单 |

> 这 12 项合计约 18–22 人日，必须在 V1 第一周启动，否则后期补建成本翻倍。

   │                                          ├─▶ SQL 模板（读商品/行情/评估）│
   │                                          └─▶ 规则引擎（等级/价格）      │
   └────────────────────────────────────────────────────────────┘
```

**关键耦合点（必须走明确定义的接口，不许跨层直调）**

| 调用方 | 被调方 | 方式 | 禁止 |
|---|---|---|---|
| 审核 | 图像评估 | 读 `ai_assessment` 记录（数据契约） | 直接在审核页调推理函数 |
| 审核 | 商品 | `ProductService.get_for_audit()` | 直接查 `product` 表拼字段 |
| 订单 | 商品 | `ProductService.freeze_stock()`（带行锁） | 自己写 UPDATE 扣库存 |
| 售后 | 图像评估 | 读评估快照（取证） | 重新评估（会变） |
| Agent | 业务数据 | Tool 层封装的只读查询 | 直连 DB / 复写业务逻辑 |
| 行情 | 订单 | 订单完成后发事件，行情异步聚合 | 订单服务里同步算行情 |

**智能域的隔离原则**：业务模块**不得 import agent 包**；Agent 只能通过 Tools 访问业务能力。这样撤掉 Agent 不影响交易，替换 Agent 不用改业务代码。

## 4. 技术架构说明

### 4.1 技术选型

| 层 | 选型 | 理由 | 备选与否决原因 |
|---|---|---|---|
| 前端框架 | Vue 3（Composition API） | 团队栈、Element Plus 生态成熟、适合中后台 | 不用 React：复用现有经验 |
| 语言 | JavaScript（非 TS） | 需求方指定；用 JSDoc + ESLint 补一部分类型约束 | 不用 TS：与需求约束冲突 |
| UI | Element Plus | 表格/表单/弹窗齐全，后台开发效率高 | 不用 Ant Design Vue：生态与主题定制成本更高 |
| 图表 | ECharts 5 | 后端下发 option，前端只渲染；行情场景够用 | — |
| 构建 | Vite | 双入口构建简单，HMR 快 | 不用 Webpack：配置复杂 |
| 后端 | Python 3.11 + FastAPI | 异步原生、OpenAPI 自动生成、与 AI 生态同语言 | 不用 Django：太重，且不需要自带 admin |
| ORM | SQLAlchemy 2.x + Alembic | 成熟、迁移可控 | 不用 Tortoise：生态弱 |
| 数据库 | MySQL 8.0 | 事务/行锁/窗口函数/FULLTEXT 满足需求；团队熟悉 | 不用 PG：运维习惯 |
| 智能体 | LangChain + LangGraph | 需求指定；LangGraph 的显式图更适合审核类可控流程 | 不用 AutoGen：不可控 |
| 图像 | YOLOv8-seg → ONNX Runtime | CPU 可跑、部署简单、无需 CUDA | 不用 PyTorch 直跑：依赖重、启动慢 |
| 向量 | bge-m3 + faiss（本地索引） | 无需独立服务、离线可用 | 不用 Milvus：运维成本 |
| 重排 | gte-rerank | 中文效果好 | — |
| 队列 | MySQL 表 + `SKIP LOCKED` | 不引入 MQ，降低运维面 | 不用 RabbitMQ/Redis：约束禁止 |
| 缓存 | 进程内 LRU | 单机、数据量小、避免 Redis | 不用 Redis：约束禁止 |
| 部署 | Nginx + uvicorn + systemd/NSSM | 单机可跑，也可平滑上云 | 不用 K8s：规模不匹配 |

### 4.2 后端分层与依赖规则

| 层 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| `api` | 协议转换：解析请求、调 service、组装响应、声明权限 | service、schemas | 写 SQL、写业务规则、直接 import model |
| `schemas` | 请求/响应 DTO、字段校验 | pydantic | 业务逻辑 |
| `services` | 用例编排、事务边界、权限数据过滤、发事件 | domain、repositories、core | 写 SQL 细节、直接返回 ORM 对象 |
| `domain` | 纯业务规则（状态机、等级映射、库存计算），无 IO | 仅标准库 + 少量工具 | 访问 DB、访问网络 |
| `repositories` | 数据访问，返回领域对象或 DTO | models、core | 业务判断 |
| `models` | ORM 映射 | sqlalchemy | 业务方法 |
| `agent` / `rag` / `vision` | 智能子系统 | core、repositories（只读） | 被 api 直接调用绕开 service |
| `core` | 平台能力（配置/日志/异常/安全/存储/任务） | 仅标准库与三方 | **不得依赖任何业务模块**（最底层） |

**依赖方向校验**：用 `import-linter` 在 CI 中强制"core 不得 import services/agent"、"domain 不得 import repositories"。

### 4.3 前端分层

| 层 | 职责 | 规则 |
|---|---|---|
| `views` | 页面容器：取数、组装区块、处理路由参数 | 不写复杂业务计算，下沉到 composables |
| `components` | 可复用展示组件（商品卡、评估卡、审核三栏） | 纯 props/emits，不发请求 |
| `composables` | 可复用逻辑（useTable、useUpload、useSSE、usePermission） | 无 DOM 依赖 |
| `stores` | 全局状态（用户、字典、购物/下单草稿、后台筛选） | 只放跨页共享状态 |
| `api` | 请求封装（按域拆分），统一错误处理与 trace | 不写业务分支 |
| `shared` | 两端共用：工具函数、常量、基础组件、样式 | 不含端特有逻辑 |

### 4.4 Agent 子系统架构

```
ChatService
   │ 构造初始 state
   ▼
GraphRunner ──▶ StateGraph（编译一次，复用）
   │              n0 guard → n1 context → n2 understand → n3 route
   │              → n5 retrieve → n6 rerank → n7 plan → n8 tool
   │              → n9 analyze → n10 compose → n11 self_check → n14 output
   │
   ├─▶ Checkpointer（MySQL 实现 BaseCheckpointSaver）
   ├─▶ ToolRegistry（按角色过滤可用工具）
   │      ├─ knowledge_search ──▶ RagService
   │      ├─ market_price ─────▶ MarketService（只读）
   │      ├─ product_search ───▶ ProductService（只读）
   │      ├─ explain_grade ────▶ GradeDomain（规则）
   │      └─ draft_order ──────▶ OrderService（仅生成草稿，不落库）
   └─▶ Tracer（每个节点写 agent_trace）
```

**要点**

1. 图只编译一次，进程内复用；配置版本变化时重建（不是每请求重建）。
2. 工具按 `role` 过滤：买家看不到"审核相关"工具，卖家只能查自己的商品。
3. `draft_order` 只产草稿，落库必须走 `POST /orders`（防止模型误下单）。
4. 自检不通过只重写 1 次，之后走兜底——避免无限循环烧 token。

### 4.5 图像评估流水线

```
提交审核
   │
   ├─ L1 门禁（同步，<200ms/图）：格式/大小/短边/模糊/曝光 → 不合格即拒，不占队列
   │
   ▼ 写 ai_assessment(status=排队) + 投递 job
Worker（串行，并发 2）
   │
   ├─ 原图转正（EXIF）→ 降采样到短边 1024
   ├─ ORT 推理 → 掩码
   ├─ 后处理：轮廓 → 连通域 → 类别互斥归并（霉变>坏果>油果>杂质>正常）
   ├─ L2 门禁：粒数 20~500、遮挡 ≤40%、图级置信 ≥0.35 → 不合格图剔除
   ├─ 多图汇总：先合并计数，再算比率（禁止比率的算术平均）
   ├─ 规则映射等级（读 threshold_version 快照）
   └─ 写 result + 更新 product.grade_flag + 发事件
   │
   ▼
审核队列可见（含差异标记）
```

**降级**：评估服务不可用时，商品仍可人工审核上架，评估结果异步补写，商品页标"评估中"。

### 4.6 数据架构

| 项 | 方案 |
|---|---|
| 库划分 | 单库分域（`sys_*` / `product*` / `order*` / `market*` / `kb_*` / `chat_*` / `agent_*` / `metric_*`），不拆库 |
| 读写分离 | 初期单库；上量后加只读从库承载列表与行情查询 |
| 分表 | `agent_trace`、`chat_message` 按月/季分区；其余不分区 |
| 图片 | 本地盘/NAS 挂载，DB 只存相对路径；超过 70% 容量迁对象存储 |
| 缓存 | 进程内 LRU（字典、热门商品、召回结果），TTL 5–30 分钟 |
| 一致性 | 库存用 `UPDATE ... WHERE stock - frozen >= ?` 乐观扣减；订单与库存同事务 |
| 事务边界 | 只在 Service 层开事务，Repository 不自行 commit |

### 4.7 部署架构

**初期（单机）**

```
Nginx :443
 ├─ /api/**  → uvicorn :8000（4 workers）
 ├─ /internal/** → 仅 127.0.0.1
 └─ /**      → 静态 dist（web / admin）
MySQL :3306（本机）
Worker ×1（评估）/ ×1（入库、导出）
Storage：/data/wolfberry（图片、报告、模型）
```

**演进路径（流量增长后）**

Web 无状态 → 多实例 + 负载均衡；Worker 独立扩容（评估吃 CPU）；MySQL 加只读从库；图片迁对象存储 + CDN。**架构不需要重写，只是加实例**。

### 4.8 关键技术决策（ADR）

| 编号 | 决策 | 理由 | 代价 |
|---|---|---|---|
| ADR-01 | 单体分层架构，不做微服务 | 团队 5 人、单库、业务耦合紧；微服务会带来分布式事务与运维负担 | 后期拆分需按域剥离，但分层已预留边界 |
| ADR-02 | Agent 不直连数据库，只走 Tool | 可审计、可限流、可 mock、可撤除 | 多一层封装，查询能力受限于工具 |
| ADR-03 | 等级/价格/库存判定全走规则 | 结果需可复现、可担责 | 规则维护成本，标准换版要更新映射 |
| ADR-04 | 图像评估异步化 | 同步会让提交接口卡 15 秒，用户体验差且易超时 | 审核要等评估完成，链路变长 |
| ADR-05 | MySQL 当队列 | 不引入 MQ，减少一个中间件 | 吞吐上限低（单机几千/天够用），需自己做重试与死信 |
| ADR-06 | 双前端产物，单工程 | 共用组件与工具，避免重复建设 | 构建配置稍复杂，需两套 vite 配置 |
| ADR-07 | 软删 + 审计，不物理删除 | 交易与审核数据需可追溯 | 表体积增长快，需定期归档 |
| ADR-08 | 评估快照永久保留 | 纠纷举证与模型迭代都需要历史 | 存储成本上升 |
| ADR-09 | 阈值与策略版本化 | 改阈值不能让历史结果无法解释 | 每次改动需审批与试算 |

## 6. 关键流程与模块协作

### 6.1 商品发布 → 评估 → 审核

| 步 | 模块 | 动作 | 事务 | 失败处理 |
|---|---|---|---|---|
| 1 | 文件 | 图片上传、L1 门禁、pHash | 单图独立 | 不合格即拒，提示重传 |
| 2 | 商品 | 字段校验、盗图比对、创建草稿 | 有 | 返回 400/62002 |
| 3 | 商品 | 提交：状态置待审核、写版本、发 `ProductSubmitted` | 有 | 失败回滚，状态不变 |
| 4 | 任务 | 投递评估 job | 有（同事务写 job） | 投递失败则商品仍待审核，人工可审 |
| 5 | 图像评估 | Worker 消费：推理、汇总、映射等级 | 评估自身事务 | 失败置 job 失败，商品仍可人工审核 |
| 6 | 审核 | 写 `grade_flag`、入队 | 有 | — |
| 7 | 审核 | 审核员操作：通过/改级/驳回 | 有 | 冲突检测（已审过） |
| 8 | 通知 | 通知卖家结果 | 异步 | 失败重试 |

> 关键：**第 5 步失败不阻塞第 7 步**。这是"AI 不可用不阻塞交易"的落地方式。

### 6.2 下单 → 履约

| 步 | 模块 | 动作 | 并发控制 |
|---|---|---|---|
| 1 | 订单 | 校验商品在架、资质有效、数量合法 | — |
| 2 | 订单 | 冻结库存：`UPDATE product SET stock_frozen = stock_frozen + ? WHERE id=? AND stock - stock_frozen >= ?` | 行锁 + 条件更新，影响行数 0 即库存不足 |
| 3 | 订单 | 写 order + order_item（快照）+ status_log | 同事务 |
| 4 | 通知 | 通知卖家 | 异步 |
| 5 | 订单 | 卖家确认 → 待发货；发货 → 已发货；收货 → 已完成 | 状态机校验 |
| 6 | 行情 | 订单完成发 `OrderCompleted` → 行情异步聚合 | 异步，失败不影响订单 |
| 7 | 定时 | 24h 未确认自动取消并释放冻结 | 幂等（按 order_no 判重） |

### 6.3 智能问答

```
前端 POST /chat/sessions/{id}/messages
   → ChatService：鉴权（会话归属）→ 限流 → 取/建 session
   → 构造 state（含 role、商品上下文、历史摘要）
   → GraphRunner.astream()
        n0 guard → n1 context(读 checkpoint+摘要) → n2 understand(意图+槽位)
        → n3 route ─┬─ 知识 → n5 retrieve → n6 rerank → n7 plan
                    └─ 数据 → n8 tool（多次循环）
        → n9 analyze → n10 compose → n11 self_check → n14 output
   → 每产生 delta 即 SSE 推送（含 stage 事件）
   → 结束：落 chat_message + citation + agent_run + trace
   → 异步：更新 session.summary 与画像
```

**降级链**：重排超时 → 按融合分排序；向量不可用 → 仅关键词；LLM 不可用 → 返回检索到的原文 + "生成服务暂不可用"；全链路超 25s → 输出已有片段。

### 6.4 异常与降级统一处理

```
业务抛 BizException(code, msg)
   → 全局 handler 捕获
   → 记录日志（含 trace_id、用户、参数摘要）
   → 返回 {code, message, data:null, trace_id}
   → 前端拦截器：401 跳登录、403 提示无权限、429 提示稍后、5xx 展示兜底页并给 trace_id

未捕获异常
   → handler 兜底：生产环境返回 50001 + trace_id，隐藏堆栈
   → 同时上报 error.log 与告警（错误率阈值）

外部依赖异常（模型/DB/存储）
   → 走降级开关：评估关闭 / 问答关闭 / 图片降级为占位
   → 记录降级事件，后台首页提示
```

### 7.1 核心实体

```

      │                            ├─ Assessment ── AssessmentMetric
      │                            ├─ ProductAudit
      │                            └─ ProductVersion

### 7.2 状态机汇总

| 实体 | 状态 | 迁移约束 |
|---|---|---|
| 商品 | 草稿→待审核→审核中→已上架 / 已驳回 / 已下架 / 违规下架 | 已上架改图或改级 → 回待审核 |
| 订单 | 待确认→待发货→已发货→已完成 / 已取消 / 售后中 / 已关闭 | 已发货不可取消，只能走售后 |
| 评估 | 排队→成功 / 失败 / 图像不合格 | 终态不可回退，重试新建记录 |
| 售后 | 待响应→处理中→已裁定→已关闭 | 裁定需附依据 |
| 卖家资质 | 待提交→待审核→已通过 / 已驳回→已冻结 | 冻结后不可发布 |

### 7.3 一致性策略

| 场景 | 策略 |
|---|---|
| 库存并发 | 条件更新（`WHERE stock - frozen >= qty`）+ 影响行数判断，不用乐观锁版本号 |
| 重复下单 | `client_order_id` 唯一索引 + 幂等中间件 |
| 重复审核 | `product_audit` 前查当前状态，状态不符拒绝（409） |
| 评估与商品状态 | 评估完成只更新 `grade_flag` 与 `ai_assessment_id`，不改商品状态（状态只由审核改） |
| 缓存与 DB | 缓存只放"可重建"数据（字典、热门列表），业务关键数据不缓存 |
| 事件投递 | 进程内事件 + DB 落 `event_outbox`（可选），失败可重放 |

## 8. 非功能性设计落地

### 8.1 权限模型

**三层**：功能权限（能不能点这个菜单/按钮）→ 接口权限（能不能调这个 API）→ 数据权限（能看哪些行）。

| 层 | 实现 | 位置 |
|---|---|---|
| 功能 | 登录返回 `permissions[]`，前端 `v-perm` 指令控制按钮 | `shared/composables/usePermission` |
| 接口 | `@require_perm("audit:handle")` 装饰器，从 JWT + 缓存校验 | `core/permissions/decorator.py` |
| 数据 | Repository 方法强制接 `scope`（`seller_id` / `buyer_id` / `site_id`），由 `data_scope.py` 统一注入 | `core/permissions/data_scope.py` |

**铁律**：数据权限在 Repository 拼接，不允许在 Service 里靠 if 判断（容易漏）。

### 8.2 日志

| 类型 | 位置 | 内容 | 级别 |
|---|---|---|---|
| 访问日志 | `logs/access.log` | 方法、路径、状态码、耗时、trace_id、用户 | INFO |
| 业务日志 | `logs/app.log` | 关键动作（发布、审核、下单）、耗时 | INFO |
| 错误日志 | `logs/error.log` | 异常堆栈、上下文 | ERROR |
| 评估日志 | `logs/vision.log` | 图片、参数、耗时、门禁拒绝原因 | INFO |
| 智能体日志 | `logs/agent.log` | 节点、工具、耗时、token | INFO |
| 审计日志 | DB `audit_log` | 谁、何时、对什么、改前改后 | — |

统一 JSON 格式：`{ts, level, trace_id, user_id, module, event, latency_ms, code, extra}`。轮转按天，保留 30 天（错误 90 天）。

### 8.3 异常处理规范

| 层 | 处理 |
|---|---|
| 参数校验 | Pydantic 自动校验，统一转 40001 |
| 业务规则不满足 | 抛 `BizException(61002, "库存不足")` |
| 权限不足 | `PermissionError` → 40301 |
| 资源不存在 | `NotFound` → 40401 |
| 状态冲突 | `Conflict` → 40901 |
| 第三方失败 | `ExternalError` → 503xx，**带 retryable 标记** |
| 未捕获 | 兜底 50001，隐藏堆栈，返回 trace_id |

**错误码规范**：`XXYYY`，`XX` 为模块（10 通用/20 认证/30 商品/40 订单/50 审核/60 评估/70 问答），`YYY` 为序号。**错误码集中在一个枚举文件，前后端共用一份定义**。

### 8.4 配置管理

| 层 | 来源 | 变更方式 | 适用 |
|---|---|---|---|
| L1 | 环境变量 | 重启 | 密钥、DB 连接、端口 |
| L2 | DB `sys_config` | 后台改，60s 热生效 | 业务开关、阈值、限流参数 |
| L3 | `config/settings.{env}.yaml` | 重启 | 结构性配置（中间件、日志级别） |
| L4 | 代码默认值 | 发版 | 兜底值 |

**禁止**：把阈值、开关、价格系数写死在代码里；把密钥写进 yaml 或代码。

### 8.5 安全设计

| 面 | 措施 |
|---|---|
| 传输 | HTTPS（TLS 1.2+）、HSTS |
| 认证 | bcrypt(cost=12)、JWT 短效 + Refresh、失败 5 次锁定 |
| 越权 | 接口权限点 + 行级过滤 + 关键操作二次校验归属 |
| 注入 | 全量参数化；Agent 禁自由 SQL；排序/字段白名单 |
| XSS | 富文本白名单过滤；引用片段转义；禁用 v-html 直接渲染用户输入 |
| 上传 | 扩展名+MIME 双校验、UUID 重命名、二次编码去 EXIF、目录不可执行、大小限制 |
| 防盗链 | 图片走签名 URL，有效期 10 分钟 |
| 敏感数据 | 手机号/地址加密存储 + 列表脱敏 + 日志脱敏 |
| 提示词注入 | 系统提示隔离、注入特征检测、工具参数二次校验 |
| 盗图 | pHash 比对在架图库 |

### 8.6 性能与容量

| 手段 | 落点 |
|---|---|
| 列表查询走覆盖索引 | `product(status, platform_grade_id)`、`order(buyer_id, status)` |
| 聚合预计算 | `metric_daily`、`market_price_daily` 由定时任务写入，查询不实时算 |
| 分页深翻页 | 用游标（`id < last_id`）替代大 offset |
| 图片分层 | 列表用 300px 缩略图，详情才加载原图 |
| 评估限流 | 队列深度上限 + 优先级（新提交优先于预检） |
| 问答限流 | 10 次/分钟/用户，超出 429 |

## 9. 开发规范与协作

### 9.1 规范

| 项 | 约定 |
|---|---|
| 后端风格 | ruff + black，行宽 100，禁止裸 `except` |
| 前端风格 | ESLint + Prettier，组件名 PascalCase，文件 kebab-case |
| 命名 | 接口路径用复数名词；DB 表名蛇形单数（`product`），字段蛇形 |
| 分支 | `main`（保护）+ `feature/*` + `fix/*`；PR 必须过 CI 与 1 人 Review |
| 提交 | Conventional Commits：`feat(product): 支持批量下架` |
| 接口契约 | 先写 schema，再写实现；OpenAPI 自动生成并纳入 CI 校验（不得破坏性变更） |
| 数据库变更 | 只通过 Alembic，禁止手改生产库；每个迁移必须可回滚 |

### 9.2 环境

| 环境 | 用途 | 数据 |
|---|---|---|
| dev | 本地开发 | 造数脚本 + SQLite/本地 MySQL |
| test | 联调与自动化测试 | 每次 CI 重建，跑完销毁 |
| staging | 预发验收 | 脱敏生产数据子集 |
| prod | 生产 | 真实数据，只允许走发布流程变更 |

### 9.3 测试策略

| 层 | 覆盖目标 | 工具 |
|---|---|---|
| 单元测试 | `domain/` 全覆盖（等级映射、库存、状态机、汇总） | pytest |
| 集成测试 | Service + Repository，真库事务回滚 | pytest + 测试库 |
| 接口测试 | 全部 P0 接口的契约与权限 | httpx + 断言错误码 |
| 端到端 | 发布→评估→审核→下单→发货→收货 | Playwright（可选） |
| RAG 评测 | 100 条问答集，跑 Recall/引用准确率 | `scripts/eval_rag.py` |
| 算法评测 | 500 张标注图，mAP/准确率/计数误差 | 离线脚本 |
| 压测 | 列表/详情/下单/问答并发 | Locust |

### 9.4 代码评审关注点（Checklist）

- [ ] 是否在 Router 里写了业务逻辑或 SQL
- [ ] `domain/` 是否引入了框架依赖
- [ ] 写操作是否落审计
- [ ] 查询是否拼了数据范围（能否越权）
- [ ] 阈值/开关是否硬编码
- [ ] 异常是否用了统一错误码，文案是否可给用户看
- [ ] 是否有 N+1 查询、全表扫描
- [ ] 新增权限点是否登记到 registry
- [ ] 是否补了单测（domain 必测）

### 10.4 风险

| 范围蔓延（支付/物流/营销） | 高 | 工期失控 | 不做项写入合同附件；新需求走变更评估 |
